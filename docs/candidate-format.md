# 候補JSONと入力列

`--candidate` はAI生成前に検証器を確かめるための手書き候補を読み込みます。APIも同じJSONを返します。完全な例は `examples/secure_kv_ivw.json` です。

トップレベルは次の3フィールドのみです。ソースの変更は `changes` と `files` のどちらか一方で書きます。

- `changes`: `{ "path": "ta/entry.c", "defect": "D1", "old": "元の行", "new": "置き換える行" }` の配列。`old` は正常版のそのファイルにちょうど1回だけ現れる文字列で、行をそのまま写します。挿入は、隣の行を `old` と `new` の両方に書いて表します。`defect` はその変更が属する不備のIDです。同じファイルの変更どうしは重なってはいけません。別の不備の変更とのあいだには、変更しない行を1行以上残します。最大64個。AIにはこの形式で返させます（ソース全文を書き直させないため）。
- `files`: 既存の相対パスから変更後の全文への対応。手書き候補ではこちらも使えます。
- どちらも対象は `ta/` 以下の既存の `.c` / `.h` に限ります。
- `defects`: `id`、`class`、`detector_targets`、`witness_test_ids`、`reason`。`files` で書く場合だけ `edits` も必要です。
- `tests`: 通常入力と発火入力。AIが観測や合否を記入することはできません。

編集は、ファイル名の辞書順で、文脈0行の行差分の連続単位に `E1` から順にIDを振ったものです（行のまとまりをそのまま別の場所へ移した場合は、削除と挿入を合わせて1つの編集 `move`）。行範囲はツールが実際の差分から求めます。すべての編集がちょうど1つの不備に属する必要があります。`changes` では、編集はその行に触れる変更の `defect` に属します。1つの変更が複数の編集になってもかまいませんが、別の不備の変更と隣り合って1つの編集にまとまる場合は拒否します。`files` では、各不備の `edits` にIDの配列を書き、実際の差分と一致するか確認します。

`detector_targets` は `{ "path": "ta/entry.c", "function": "関数名", "lines": [開始, 終了], "role": "effect" }` の配列です。AIは、不備の影響が実行経路上で最初に生じる操作（`effect`）を1件指定します。対応する保護操作（`protection`）が不備版に残っていれば、不十分な場合や実行が遅すぎる場合もその位置を1件指定し、欠落していれば要素を省略します。各操作は原則1行、必要なら最小の連続範囲とし、行番号は1始まりで両端を含みます。両方が同じ行でも構いません。要素のキーはこの4つに限ります。検出器の報告とどう照合し集計するかは、データセットを使う側が決めます。

影響操作・保護操作のどちらも、空白、コメント、括弧やセミコロンなどの区切り記号だけを含む範囲は検証エラーになります。

各テストの形式:

```json
{
  "id": "T02",
  "purpose": "witness",
  "targets": ["D1"],
  "witness_step": 2,
  "steps": [
    {"op": "open", "session": "s1"},
    {"op": "invoke", "session": "s1", "command_id": 0,
      "params": [
        {"type": "value_inout", "a": 8, "b": 42},
        {"type": "none"}, {"type": "none"}, {"type": "none"}
      ]},
    {"op": "close", "session": "s1"}
  ]
}
```

`purpose: normal` の場合は `targets: []` とし、`witness_step` を省略します。`witness_step` はステップ列全体の1始まりの位置で、invokeを指します。すべてのテストにはinvokeが必要です。セッションを開いてから使用し、同じ名前の再オープンはclose後に行います。UUIDは正常TAのヘッダから自動検出します。

パラメータは必ず4個指定します。

| type | 入力フィールド |
|---|---|
| `none` | なし |
| `value_input` / `value_output` / `value_inout` | `a`, `b`（uint32、既定0） |
| `memref_input` / `memref_inout` | `data`（偶数桁のhex。区切りの空白は書いてもよく、検査時に取り除きます）、`size`（省略時はデータ長） |
| `memref_output` | `size`（出力領域の容量） |
| `shared_memref_input` / `shared_memref_inout` | `data`, `size`（実共有バッファ） |
| `shared_memref_output` | `size`（実共有バッファの出力容量） |

`size` の単位はバイトで、`data` のhex 2桁が1バイトに対応します。入力の `size` を省略するとデータ長を使い、データより大きい `size` を指定すると残りを0で埋めます。例えば `{"type":"memref_input","size":65,"data":"41"}` は先頭が `41`、残り64バイトが0の入力です。データ長が `size` を超えると、テストID・ステップ番号（1始まり）・パラメータ添字（0始まり）・両者のバイト数を示して拒否し、その理由を次のAI試行へ渡します。

コマンドID・valueは0〜4294967295、バッファは最大1MiB、各列は最大256ステップです。同時セッションは16、異なるセッション名は列全体で32までです。1計画は蓄積通常入力を含め最大256テストです。初版の制限を超える計画は静的検査で拒否します。

実測観測は `op`、`result`（数値のTEE戻り値）、`origin`、`params`、`ta_crashed` です。成功時のoriginはAPI上で未定義なため0に正規化します。出力memrefでは返却されたサイズと取得できたバイト列を記録します。バッファ容量を超える返却サイズは記録しますが、容量を超えたメモリは読みません。closeにはAPI戻り値がないため0を記録します。プロセス異常や観測欠落を架空のTEE戻り値へ変換しません。

TAと分類の組合せに対応できない場合、APIは `{"unsupported": "具体的な理由"}` を返せます。ツールは別分類への変更や件数合わせを行いません。

## 前のステップの出力を入力に使う

TAが返したハンドルやトークンのように、起動ごとに変わる値を後の入力に含めたい場合は、
入力バッファ（`memref_input`、`memref_inout`、`shared_memref_input`、`shared_memref_inout`）に
`inserts` を指定します。実行イメージには `output_reference_v1` が必要です。

```json
{"type": "memref_input", "size": 82, "data": "00000000",
 "inserts": [{"offset": 16, "from": {"step": 2, "param": 1, "offset": 8, "length": 58}}]}
```

この指定は、`data` と0埋めで入力を作ったあと、同じテストのステップ2（1始まり、invokeに限る）の
パラメータ1（0始まり）の出力バッファの8バイト目から58バイトを、この入力の16バイト目へ複写します。

- 複写元は、より前のinvokeの出力またはinoutバッファに限ります。
- 複写元の範囲は複写元の容量内、複写先の範囲はこの入力の `size` 内に限ります。
- 1パラメータにつき最大8件、1つの入力列で参照できる出力は最大64個です。
- 複写するのは呼出し後のバッファの内容です。TAが書き込まなかった部分は0です。複写元の呼出しが失敗していても、計画は最後まで実行します。
- 値パラメータ（`value_input`、`value_inout`）にも同じ `inserts` を書けます。値パラメータは8バイト（`a` の4バイト、`b` の4バイトの順、リトルエンディアン）として扱い、複写元にも複写先にもできます。たとえば、ステップ2のパラメータ1が `b` に返したハンドルを `a` に入れるには、`{"type": "value_input", "inserts": [{"offset": 0, "from": {"step": 2, "param": 1, "offset": 4, "length": 4}}]}` と書きます。
- 別テストの出力の参照、演算や条件は指定できません。

同じ指定を正常版・欠陥版・編集を戻した版に適用します。観測には、複写後の入力バイト列がそのまま残ります。
複写元の出力が実行ごとに変わる場合、複写先のステップの観測も実行ごとに変わります。

## 呼出し途中の入力変更

AIは `invoke` の `events` に、停止位置と入力操作をデータとして指定できます。
実行イメージには `shared_memory_events_v1` が必要です。完全な手書き例は
`examples/shared_record_dus.json` にあります。

```json
"events": [{
  "trigger": {
    "kind": "checkpoint",
    "path": "ta/entry.c",
    "function": "update_record",
    "before": "state->value = request->value;",
    "occurrence": 1
  },
  "action": {
    "kind": "write_memory",
    "param": 0,
    "offset": 0,
    "expect": "02000000",
    "data": "09000000"
  }
}]
```

この指定は、関数内の代入文に初めて到達したとき、その直前でTAを一時停止し、
パラメータ0の共有入力の先頭4バイトが `02000000` であることを確認して
`09000000` に変更し、TAを再開します。`param` は0始まり、`offset` はバイト単位です。
`occurrence` は各invoke内で1始まり、最大1024です。同じ停止位置で複数の操作を指定できます。

`before` は、正常版・欠陥版・各編集を戻した版で共通する既存の1行の文を指定します。
関数内で一意に一致する代入文または関数呼出し文だけを受け付けます。
宣言、制御文、ラベル、複数行の文、マクロ内などは対応しません。
AIがTAへ観測用のフラグやフックを追加する必要はありません。
信頼する実行器がビルド用コピーにだけ同期点を挿入します。

操作対象は `shared_memref_input` または `shared_memref_inout` です。
通常の `memref_*` は一時バッファなので途中変更には使いません。
`expect` と `data` は同じ長さの非空hexで、最大4096バイト、宣言した容量内に限ります。
1invokeにつき最大16イベント、計画全体で最大64停止位置です。
イベントは配列順に実行します。到達しない位置、順序の食い違い、期待値の不一致は検証失敗です。
任意のアドレスへのアクセス、遅延時間の指定、自由記述の実行コードは受け付けません。

同じ固定済みのイベント列を、R1〜R3と不備の切り分けのすべてに適用します。観測の `events` には
停止位置ID、到達回数、対象パラメータとオフセット、実測した変更前後のバイト列を保存します。
予定と観測が一致しない結果は採用しません。共有メモリの変更だけでは合格せず、
TAの戻り値・出力・読戻し状態に再現する差が必要です。
`verification.json` の `semantic.execution` に実行機能と停止位置を保存し、
`work/.../builds/.../instrumentation.json` に元ソース・計装後ソースのハッシュと行位置を残します。
元ソース、ケースの `source/`、ブラインド出力には同期点を含めません。

これは指定した順序を強制した実験です。自然なスケジューリングでの競合発生率を測るものではありません。
チェックポイントの追加がコンパイラ最適化やタイミングに影響し得るため、
その位置が目的の検証と使用の間にあるか、差が分類の意味に合うかは人が確認します。

## 分類と実行機能の追加

分類は `config/classes.yaml` で追加できます。`required_features` は実行器に要求する機能、
`witness_conditions` は発火テストの追加条件です。既存の
`normal_error_at_witness`（正常版が発火ステップでエラー）と
`shared_memory_changed`（両版で発火ステップ中の共有入力の実変更を観測）を選択できます。
従来の `extra_condition` も互換性のため受け付けます。

既存の操作と条件で表現できる分類なら、分類名ごとのコード追加は不要です。
新たなトリガーや操作が必要な場合は `runtime/events.py` のレジストリ、対応する
共通クライアント／実行イメージ、形式検査とテストを追加します。
意味上の追加条件は `verification/conditions.py` へ実装します。
AIが未知の方式を自由なコードで生成して直ちに採用する仕組みではありません。

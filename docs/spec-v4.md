# TA設計不備ベンチマーク生成ツール 設計仕様書 v4

Nov 14, 2026 · @yoshinaga

状態：実装前の設計案（未実装・未検証）。v3を簡素化し、機械検証の範囲を「挙動差の確認」に絞った版です。

## 1. 目的と方針

正常なOP-TEE TAに、AIが指定分類の設計不備をTAソースの最小変更で挿入する。正常版と不備版に同じ入力を流して挙動の差を確認し、差が確認できたものだけをベンチマーク候補として保存する。分類と位置が正しいかは、人がレビューで判断する。

機械が保証するのは次の1点だけとする。

> このパッチを入れると、この入力のときに、正常版と挙動が変わる。

「それがIVWである」「報告すべき場所はこの行である」という意味の判断は、機械検証の範囲に含めない。

方針は6つ。

1. **正常TAは置くだけ。** 指定フォルダにTAのフォルダをそのまま置き、パスで指定する。マニフェストや基準観測の事前登録は作らない。
2. **正常版は毎回実行する。** ケース生成のたびに、AIが作った入力列を正常版と不備版の両方に流して比較する。
3. **AIが変更できるのはTA側のソースだけ。** 入力を流す実行側は両版で同一にする。これにより、出力の差は必ずTAの変更に由来する。
4. **判定ルールは分類に依存しない最小限にする。** 分類の説明はAIへのプロンプトに書くもので、機械判定には使わない。
5. **不備ケースは4要素で保存する。** `source/`、`labels.json`、`changes.diff`、`verification.json`。
6. **コマンドは2種類。** `ta-bench generate` と `ta-bench review`。

## 2. ディレクトリ構成

正常TAはフォルダを置くだけ、不備ケースは1フォルダに4要素、途中経過はすべて `work/` に置く。

```text
ta-benchmark-generator/
├── README.md
├── pyproject.toml
├── config/
│   ├── classes.yaml            # 分類の説明（プロンプト用）と対応状況
│   └── requests.example.yaml   # 複数の生成要求をまとめる例
├── docker/
│   └── Dockerfile              # 実行環境（OP-TEE・QEMU・ツールチェーンの版を固定）
├── src/ta_bench/
│   ├── cli.py                  # generate / review の入口
│   ├── generate.py             # AI: 入力列・パッチ・ラベルの生成
│   ├── check.py                # 静的検査（許可パス・編集帰属・リーク・重複）
│   ├── run.py                  # ビルド、QEMU起動、入力列の実行
│   ├── judge.py                # 最小ルールと不備の切り分け
│   ├── dataset.py              # スキーマ、ハッシュ、原子的保存
│   ├── invoke/                 # 汎用呼び出しツール（全TA共通の実行側）
│   └── review/app.py           # ローカルチェックサイト、ブラインド出力
├── benchmark/
│   ├── normal/
│   │   └── secure_kv/          # TAフォルダをそのまま置く（ta/, host/, Makefile 等）
│   └── defective/
│       └── case_8af2c61e9d5b4a6f/
│           ├── source/         # ビルド可能な不備版一式
│           ├── labels.json
│           ├── changes.diff
│           └── verification.json
├── work/                       # 試行、失敗理由、API応答、ログ、通常入力の蓄積
└── tests/
```

- `benchmark/defective/` は分類で階層化しない。ケースIDは乱数から作り、分類・生成順・正常TA名を含めない。
- `benchmark/defective/` に入るのは機械検証を通ったケースだけ。レビュー前後の区別は `labels.json` の状態で管理し、`accepted/` は作らない。
- `work/` は配布しない。生成過程を研究として報告する場合は別途保存する。

## 3. 正常TAと実行側

正常TAは `benchmark/normal/<名前>/` にフォルダごと置き、`--ta` でパスを指定する。事前の登録作業は不要で、所定の環境でビルドできることだけが条件になる。

### 3.1 正常TAの扱い

- **基準観測は保存しない。** 正常版は各ケースの検証で毎回実行するので、動くことはその場で確認できる。
- **正常版は書き換えない。** 各ケースは正常版ソースのハッシュを記録する。正常版を変更すると、参照しているケースは表示上 `stale` になる。変更したい場合は別名のフォルダとして置く。
- **正常版が無欠陥であるとは主張しない。** 比較の基準として使うだけである。

### 3.2 実行側は全TA共通の汎用呼び出しツールにする

入力列の実行には、TAごとのドライバではなく、全TA共通の小さな呼び出しツールを1つ使う。TEE Client APIはTAによらず同じ形（UUID、コマンドID、4つのパラメータ）なので、TA固有の実装は要らない。

- **入力：** ステップの列。各ステップは、セッションの開始・終了、またはコマンド呼び出し（コマンドIDと4パラメータの型・値・バッファ内容）。
- **出力：** 各ステップの戻り値、エラーの発生元、出力パラメータの値とバッファ内容、TAの異常終了の有無。
- **UUID：** 正常TAのヘッダから読み取る。

このツールは正常版と不備版で同じバイナリを使う。AIが作るのは入力列（データ）だけで、実行側のコードは作らせない。状態の読戻しが必要な場合は、TAが元から持つコマンドを入力列に含めて行う。

### 3.3 AIが変更できる範囲

- 既定の許可は `ta/` 配下の `.c` と `.h` のみ。`host/`、Makefile、`.mk`、スクリプトへの変更は即失敗にする。
- AIの申告は信用せず、正常版と不備版の全ファイルを比較して変更パスを確認する。
- パスは正規化し、`..`、絶対パス、シンボリックリンク、ファイルの追加・改名による迂回を拒否する。
- ビルドとQEMUは隔離環境で実行する。ネットワーク無効、秘密情報なし、時間とメモリの上限あり。

### 3.4 初期状態と非決定性

- 各実行は独立した初期状態から始める。最初の版では、実行ごとに同じイメージからQEMUを起動し直す。遅ければ後でスナップショットに置き換える。
- 乱数や時刻で出力が変わるステップがあると、比較が成り立たない。そこで正常版と不備版をそれぞれ2回実行し、同じ版の2回の間で値が一致しなかった項目（戻り値、出力の長さ、各バッファの中身など）だけを比較対象から外す。バッファは中身が1バイトでも違えば中身全体を外す。同じステップの残りの項目は比較する。発火ステップ以降の差が外した項目の中にしかない場合は `unknown` とする。

### 3.5 実行環境

開発でも公開後でも、Dockerイメージ1つを実行環境とする。macでもLinuxでも同じ手順で動かし、Dockerを使わない手順は保証しない。

- **イメージの中身。** OP-TEE、QEMU、ツールチェーン、汎用呼び出しツールを入れる。
- **版の固定。** Dockerfileでは、ベースイメージとOP-TEEマニフェストのリビジョンを固定する。イメージはタグではなくダイジェストで指定し、`verification.json` の `image_digest` に記録する。
- **配布。** Dockerfileに加えて、ビルド済みのイメージをレジストリに置く。OP-TEE一式のビルドは長時間かかるためである。
- **QEMUの起動。** OP-TEEのQEMU構成はセキュアワールドをソフトウェアでエミュレートするので、KVMや特権は使わない。画面なしで起動し、シリアル出力はファイルに書き出す。
- **生成と検証の分離。** AIのAPIを呼ぶ生成側はネットワークを使う。ビルドとQEMUを動かす検証側は、ネットワークを無効にし、秘密情報をマウントせず、CPU・メモリ・時間に上限を付けたコンテナで実行する。
- **macでの開発。** OP-TEEのビルドツリーはDockerボリュームに置き、macのフォルダは編集するソースだけをマウントする。Apple Siliconでは、arm64のコンテナでツールチェーンの取得が通るかを最初に確認する。
- **成果物として残す検証。** Linuxのamd64に固定する。アーキテクチャが違うとイメージもツールチェーンも別物になり、`image_digest` が一致しないためである。macでの実行結果は開発用とし、`benchmark/` には保存しない。

## 4. 不備ケースのデータ仕様

1ケースは `source/`、`labels.json`、`changes.diff`、`verification.json` の4要素で構成する。以下のJSONは構造を示すための架空の例で、実験結果ではない。

### 4.1 `labels.json`

```json
{
  "schema_version": "4.0",
  "case_id": "case_8af2c61e9d5b4a6f",
  "normal": {
    "path": "normal/secure_kv",
    "source_digest": "sha256:<digest>"
  },
  "defects": [
    {
      "id": "D1",
      "class": "IVW",
      "edits": [
        {
          "edit_id": "E1",
          "path": "ta/entry.c",
          "kind": "delete",
          "normal_lines": [85, 88],
          "defective_lines": null
        }
      ],
      "detector_targets": [
        {
          "path": "ta/entry.c",
          "function": "TA_InvokeCommandEntryPoint",
          "lines": [86, 86],
          "role": "effect"
        }
      ],
      "witness_test_ids": ["T02"],
      "reason": "外部由来の添字を範囲検査せずに使用する"
    }
  ],
  "review": {
    "status": "unreviewed",
    "reviews": [],
    "approved_against": null
  }
}
```

- **`edits` は変更箇所の記録、`detector_targets` は検出器の報告と照合する正解位置。** 別の概念として分ける。
- 位置ラベルは不備ごとに影響操作（`effect`）1件と、存在する場合のみ保護操作（`protection`）1件を記録する。ORDERでは先に成功すべき保護操作と、それに先行した影響操作を区別する。
- `detector_targets` は不備版のソース上に実在する行を必須とする。検査を削除した不備では、消えた行ではなく、検査がなくなって危険になった使用箇所を指す。
- 行番号は1始まりで両端を含む。削除では `defective_lines` が `null`、挿入では `normal_lines` が `null`。両方 `null` は不正。
- 同じファイル内で、ある場所から消えた行がそのまま別の場所に入った場合（字下げの違いは無視）は、削除と挿入を合わせて1つの編集単位 `move` とする。`normal_lines` は元の位置、`defective_lines` は移動先。片方だけを戻すと行が二重になるため、不備を戻すとき（5.2節）も一緒に戻す。この扱いを入れる前に、移動を削除と挿入の2つの編集として保存したケースは、保存時の数え方のまま有効とし、再検証も同じ数え方で行う。
- 編集単位（`E1` など）は、文脈0行の行差分のまとまりとして機械的に求める。すべての編集単位は、ちょうど1つの不備に帰属しなければならない。
- `class` は `config/classes.yaml` に定義した分類名のいずれか。分類の個数と名称は固定せず、このファイルを書き換えれば変わる。サブタイプは持たない。
- 人による位置の修正は該当不備の `detector_targets` に反映する。レビュー判断は `review` に、位置の変更前後はケース内の `label_history.json` に保存する。

### 4.2 `changes.diff`

正常版を左、不備版を右としたUnified Diff。両ソースから機械的に生成し、`review` の起動時に再計算して一致を確認する。人が読むためのもので、編集単位の帰属は `labels.json` 側で管理する。

### 4.3 `verification.json`

```json
{
  "schema_version": "4.0",
  "case_id": "case_8af2c61e9d5b4a6f",
  "environment": {
    "optee_revision": "<revision>",
    "qemu_revision": "<revision>",
    "toolchain": "<version>",
    "image_digest": "sha256:<digest>",
    "runner_version": "<version>"
  },
  "generation": {
    "model_id": "<model-id>",
    "attempt_index": 2,
    "attempts_total": 2,
    "plan_digest": "sha256:<digest>"
  },
  "semantic": {
    "tests": [
      {
        "id": "T01",
        "purpose": "normal",
        "targets": [],
        "steps": ["<入力ステップ列>"],
        "observed": {"normal": ["<観測列>"], "defective": ["<観測列>"]},
        "equal": true
      },
      {
        "id": "T02",
        "purpose": "witness",
        "targets": ["D1"],
        "witness_step": 2,
        "steps": ["<入力ステップ列>"],
        "observed": {"normal": ["<観測列>"], "defective": ["<観測列>"]},
        "equal": false
      }
    ],
    "defect_reverts": [],
    "machine_validation": {
      "status": "machine_pass",
      "per_defect": {"D1": "machine_pass"},
      "repetitions": 2
    }
  },
  "run_meta": {"verified_at": "<ISO-8601>", "run_id": "<run-id>"}
}
```

- **`semantic`** は判定に関わる内容（入力、観測、比較結果、不備ごとに戻した結果、機械判定）。承認ハッシュの対象になる。
- `defect_reverts` は、複数の不備を含むケースで不備を1つずつ戻した結果（5.2節）。不備が1つのケースでは空。編集単位を1つずつ戻していた時期に保存したケースには `necessity` が残るが、読まない。
- **`run_meta`** は日時や実行IDなど、判定に関わらない情報。更新しても承認は失効しない。
- `observed` には、呼び出しツールが実際に取得した値だけを入れる。AIの説明文や自己評価は入れない。
- `generation.plan_digest` は、初回の実行前に固定した入力列のハッシュ。実行後に入力列を書き換えていないことを手順として示すもので、外部への証明にはならない。
- 大きなログやQEMUイメージはケースに複製せず、`work/` に置く。

## 5. 生成と検証のフロー

1回の試行は「生成、静的検査、対照実行、不備の切り分け、保存」の順に進む。QEMUを使わない安い検査を先に置き、通った候補だけを実行する。

静的検査から不備の切り分けまでのどこで落ちても、理由を記録して生成に戻る。保存されるのは全段階を通った候補だけである。

### 5.1 手順

1. **生成。** AIが入力列（通常入力と発火入力）、パッチ、ラベルを出す。入力列はこの時点でハッシュを取って固定する。
2. **静的検査。** QEMUを使わずに次を確認する。
   - 変更が許可パス内に収まっている。
   - すべての編集単位が、いずれか1つの不備に帰属している。
   - `detector_targets` の行と関数が不備版に実在する。
   - 追加・変更された行のコメント、識別子、文字列に、分類名や不備を示す語がない。
   - 同じ正常TAの既存ケースと、正規化した差分（正常版での位置を含む）が重複していない。また、正常版の同じ行を編集し、照合位置も同じケースがない。別の正常TAのケースや、同じTAでも別の行への編集は、照合位置が同じでも重複としない。
3. **ビルド。** 不備版をビルドする。正常版のビルドはキャッシュを使う。
4. **対照実行。** 同じ入力列を、独立した初期状態の正常版と不備版に流す。蓄積してある通常入力もあわせて流す。
5. **判定。** 5.2節のルールを当てはめる。
6. **不備の切り分け。** 複数の不備を含むケースだけで行う。不備を1つずつ、その編集単位をすべて正常版の内容に戻してビルドし、その不備の発火入力を再実行する。
7. **保存。** すべて通ったケースだけを、4要素そろえて `benchmark/defective/` に原子的に保存する。初期状態は `unreviewed`。

途中で落ちた試行は理由とともに `work/` に残し、上限内なら1に戻る。上限に達したら未達として集計し、件数合わせはしない。

### 5.2 判定ルール

判定は分類によらず、次の3つで行う。

| ルール | 内容 | 落とせるもの |
| --- | --- | --- |
| R1 通常入力の一致 | 通常入力では、全ステップの観測が両版で一致する | 機能を壊しただけのパッチ |
| R2 発火入力での差 | 発火入力では、指定したステップ以降で観測が両版で異なる。正常版は異常終了しない | 挙動に現れない変更 |
| R3 再現 | 発火入力を2回実行し、同じ観測が得られる | 偶然の差 |

- 分類ごとに条件を1つだけ追加できる。たとえばIVWでは、R2に「正常版はそのステップでエラーを返す」を加える。追加条件は `config/classes.yaml` に書く。
- 複数の不備を含むケースでは、不備ごとに発火入力を持ち、その不備の編集をすべて戻すと観測が正常版と一致することを確認する。切り分けられない場合は `unknown` とする。不備が1つのケースでは、戻すと正常版そのものになるため行わない。
- 編集単位を1つずつ戻す確認は行わない。不要な変更が混ざっていないかは機械では確認せず、レビューで差分を見て判断する（6.1節）。
- R1で使う通常入力はAIが選ぶため、壊れた機能を通らないことがある。対策として、過去のケースで使った通常入力を正常TAごとに `work/` に貯め、新しいケースにも流す。

### 5.3 機械判定の状態

| 状態 | 意味 | 保存先 |
| --- | --- | --- |
| `machine_pass` | R1からR3をすべて満たし、複数不備では切り分けもできた | `benchmark/defective/` |
| `machine_fail` | いずれかのルールを満たさなかった | `work/` |
| `unknown` | 非決定性や切り分け不能で判定できなかった | `work/` |
| `unsupported` | その分類または正常TAとの組合せに未対応 | `work/` |
| `execution_error` | ビルドやQEMUの実行に失敗した | `work/` |

DUSは共有メモリを検証と使用の間で書き換える必要があり、逐次呼出しだけでは決定的に発火できない。初版では `unsupported` とした。実行器4.1以降は入力列の `events` で停止位置・期待値・共有入力の変更を指定し、同じ固定済みの順序を正常版・不備版・復元版で実行する。詳細と制限は [candidate-format.md](candidate-format.md) の「呼出し途中の入力変更」を参照する。同期点はビルド用コピーにのみ挿入し、配布ソースには含めない。古いイメージや表現できない組合せは引き続き `unsupported` とし、別の分類にすり替えない。

### 5.4 コマンド

```bash
# 1ケースに1不備。IVWを1件含むケースを5個
ta-bench generate --ta benchmark/normal/secure_kv --defects IVW=1 --count 5

# 1ケースに複数不備。IVWを2件とUDOを2件含むケースを3個
ta-bench generate --ta benchmark/normal/secure_kv --defects IVW=2,UDO=2 --count 3

# 内訳の違う要求をまとめて実行する場合は要求ファイルで指定
ta-bench generate --request config/requests.example.yaml

# 中断した実行の未完分を再開
ta-bench generate --resume <run-id>
```

`--defects` は1ケースに含める不備の内訳、`--count` はその内訳のケースを何個作るかを指定する。要求数は機械合格候補の目標であり、保証件数ではない。終了時に要求数、保存数、未達数、理由を表示する。

## 6. レビューと承認

分類・位置・挙動の意味が正しいかは、人がチェックサイトで不備ごとに確認する。機械判定やAIの説明で、人のチェックを埋めることはしない。

```bash
# ローカルチェックサイトを起動
ta-bench review --dir benchmark/

# 保存済みケースをQEMUで再検証
ta-bench review --dir benchmark/ --reverify
```

### 6.1 確認する3項目

| 項目 | 人が判断すること | 機械が用意する材料 |
| --- | --- | --- |
| 分類 | その不備が、定義に照らして指定の分類に当たるか | 分類の定義、変更理由 |
| 位置 | `detector_targets` が、検出器が報告すべき場所として妥当か | 差分のハイライト、編集単位の帰属 |
| 挙動 | 観測された差が、意図した不備の結果として説明できるか | 入力列、両版の観測、差のあるステップ |

- 一覧画面には、ケースID、正常TA、分類と件数、機械判定、レビュー状態、整合性の警告を表示する。
- チェックのたびに `labels.json` の `review` を原子的に保存する。
- 機械判定が `machine_pass` のケースで、3項目を確認した不備から個別に承認できる。全不備を承認するとケース全体が承認済みになる。
- 正解位置は不備ごとに編集できる。ファイル・関数・行範囲を不備版のソースで検証し、修正した不備の以前の承認を失効させる。
- 却下には不備ごとに理由を付ける。保留は `in_review` のままにする。不備に必要のない変更が差分に混ざっているケースは却下する。
- 評価者の記録は `reviews` の配列に追加する。既定は1名で承認可能とし、複数名による確認は設定で要求できる。

### 6.2 承認ハッシュ

承認時に、次の5つのハッシュをまとめて `approved_against` に保存する。

1. 正常版ソース
2. 不備版ソース
3. `changes.diff`
4. `labels.json` のうち `review` を除く全体
5. `verification.json` の `semantic`

- `review.per_defect` は不備別の状態と承認対象のハッシュを持つ。ハッシュに含めるラベルは当該不備とその修正履歴に限定する。以前のケース全体の判断も読み込める。
- `review.status` は `unreviewed`、`in_review`、`partially_approved`、`approved`、`rejected` のいずれか。一部の不備を承認済みの場合は `partially_approved` とする。
- **`stale` は保存しない。** 表示のたびに現在のハッシュを計算し、承認時と違えば `stale` と表示して再承認を求める。
- `--reverify` で観測と判定が前回と同じなら、日時が変わっても承認は維持する。違えば失効し、古い結果は `work/` に退避する。
- 起動時には、4要素の有無、スキーマ、正常TAの存在、差分の再計算、編集単位の帰属、`detector_targets` の実在を検査する。壊れたケースは承認させない。
- 通常の起動では、AI生成もQEMU実行も行わない。サイトは既定でローカルホストにのみ公開する。LAN内への公開は、起動時に `--host` で明示した場合に限る。

## 7. ブラインド出力と評価手順

検出器には不備版のソースだけを渡し、正常版・入力列・ラベル・差分は渡さない。そのための出力は `review` のオプションで行う。

```bash
ta-bench review --dir benchmark/ --export-blind ./evaluation-input --approved-only
```

- 元の `benchmark/` は変更せず、別のディレクトリにソースだけを複製する。
- ケースIDは無関係な乱数IDに振り直す。乱数IDと正解ラベルの対応表は、評価者側に別途保存する。
- `labels.json`、`changes.diff`、`verification.json`、レビュー記録は出力に含めない。
- 出力するのは既定でTA側のソースとする。host側を含めるかはオプションで選ぶ。
- 検出器には1ケースずつ、独立したセッションで渡す。同じ正常TAから作ったケースを並べて見せると、ケース間の差分で不備位置が分かるためである。
- 照合の粒度（行一致、関数一致など）は評価の前に決め、結果を見てから広げない。
- LLMを使う検出器と比較する場合は、生成モデルと検出モデルが同系統かどうかを記録し、結果を分けて報告する。

## 8. この仕様が保証しないこと

機械検証が示すのは「この入力で挙動が変わる」ことまでであり、次の点は保証しない。論文や報告では限界として明記する。

- **分類の正しさ。** 分類が妥当かどうかは、人のレビューによる判断である。
- **未試験の入力での挙動。** 保存した入力列以外での正しさや、ほかの不備がないことは示さない。
- **正常版の無欠陥性。** 正常版は比較の基準であり、欠陥がないとは主張しない。
- **不備の種類の網羅性。** 入力列と対応済みイベントで再現し、外から差を観測できる不備だけが合格する。出力に現れない不備や、対応する操作・観測方法がない不備は含まれない。イベントは強制した順序での実験であり、自然な競合発生率は測らない。
- **入力列の事前固定の外部証明。** ハッシュは手順を示すだけで、実行前に確定したことの第三者への証明にはならない。
- **リークの完全な防止。** コメントや識別子の走査は露骨な語を拾うだけで、人の確認も必要である。
- **原因の多様性。** ケースの本数と、独立した原因の数は別である。定数や名前だけを変えたケースを別の原因として数えない。

## 9. 最小完成条件と開発順序

最初の到達点は「正常TA1種類、1分類、1不備」で、生成からレビューまでが一通り動くことである。

### 9.1 最小完成条件

- [ ] 正常TAをフォルダに置き、パス指定でビルドと実行ができる。
- [ ] 汎用呼び出しツールで入力列を流し、各ステップの観測を取得できる。
- [ ] 許可パス以外を変更したパッチが、実行前に失敗する。
- [ ] 同じ入力列を両版に流し、R1からR3で判定できる。
- [ ] 機械合格したケースが4要素で保存され、`detector_targets` が不備版の実在行を指す。
- [ ] チェックサイトで差分・観測・ラベルを表示し、3項目のチェック、承認、却下を保存できる。
- [ ] ソースやラベルを変更すると `stale` と表示され、再検証で結果が同じなら承認が維持される。
- [ ] ブラインド出力に、乱数IDのソースだけが含まれる。

### 9.2 開発順序

1. Dockerイメージを作り、その中でOP-TEEのビルドとQEMUの起動を確認する。続けて、汎用呼び出しツールと観測の取得を作る。
2. **手書きのパッチで判定側を確かめる。** 合格するはずの不備を1つと、落ちるはずのパッチを数個用意する。落ちる側は、Makefileを触るもの、機能を壊すもの。それぞれが想定した段階で落ちることを確認する。
3. 4要素の保存形式とスキーマを確定する。
4. `generate` にAIの生成と試行上限を接続する。
5. `review` に一覧、差分、観測、チェック操作、承認ハッシュを実装する。
6. ブラインド出力を実装する。
7. 複数不備、ほかの分類、正常TAの追加へ広げる。

### 9.3 最初の版で作らないもの

正常TAごとのマニフェストとドライバ、分類の意味全体を証明する判定述語、意味を変えない変更だけを入れた陰性例、検出器比較機能の内蔵、データベース、大きなダッシュボード。DUSの呼出し途中の共有入力変更は実行器4.1で追加した。

## 10. v3からの変更点

v3の信頼境界（AIはTA側だけを変更できる）と照合位置の考え方は残し、事前登録と分類別の判定を外した。

| 項目 | v3 | v4 |
| --- | --- | --- |
| 正常TAの登録 | `manifest.json` に実行契約と基準観測を固定 | フォルダを置いてパス指定。基準観測なし |
| 実行側 | 正常TAごとの信頼済みドライバ | 全TA共通の汎用呼び出しツール1つ |
| 機械判定 | 分類ごとの固定述語 | 分類に依存しないR1からR3。実行器4.1では追加条件を名前のリストで選択 |
| 事前期待 | 必須予測を実測と照合 | 結果の予測は不要。入力列をハッシュで固定し、途中イベントの期待値は操作の前提条件として照合 |
| 因果の確認 | 不備ごとの復元テスト | 複数不備のケースだけ、不備ごとの復元テスト |
| 位置情報 | 両版アンカーと `detector_targets` | `detector_targets` に一本化 |
| 承認ハッシュ | 12要素 | 5要素 |
| 分類の妥当性 | 機械判定と人の両方 | 人のレビューのみ |
| 非決定性 | 個別に定める | 両版を2回ずつ実行し、同じ版の2回で一致しなかった項目だけを比較から除外 |
